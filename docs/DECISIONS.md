# Engineering decisions

This is the deeper log behind [../README.md](../README.md) — the tradeoffs I made and why, what this pipeline genuinely can't do yet, what actually broke while building it, and how I know it works beyond "the script exited 0."



## Tradeoffs

A few decisions that had a real alternative I considered and rejected, and why:

**Incremental pseudonym mapping instead of rebuilding from scratch each run.** The simpler version of this pipeline would regenerate `Customer CUST-000123` fresh every time it runs. I didn't do that, because downstream consumers need that ID to mean the same real customer next week as it does this week. The incremental version is more code (every mapping stage has to differ against what it already assigned and only touch what's new), but rebuilding from scratch would silently break identity continuity every single run.

**Subprocess orchestration instead of Airflow, for now.** I could have reached for Airflow immediately. I didn't, because right now this runs on one machine, triggered by one person, on an irregular schedule bounded by a manual Excel export. Airflow's scheduler, metadata database, and webserver solve problems I don't have yet. When there's an actual warehouse layer with real cross system dependencies to coordinate, that's when the orchestration needs outgrow a Python script, and Airflow is the planned next step at that point. Building the DAG logic into `run_pipeline.py` now means the stage dependency graph is already explicit when that migration happens.

**Fail loudly on schema drift instead of passing unknown columns through.** If the source export gains a new column tomorrow that nobody's told this pipeline about, `standardize_order_columns.py` stops the whole run rather than silently carrying an unmapped, cryptically named column all the way to the pseudonymized output. That's more annoying in the short term (someone has to go update `column_mapping.py` before the pipeline runs again) but the alternative is a raw field code from the source system sitting unnoticed in what's supposed to be clean, documented output.

**SCD Type 2 for the customer dimension: designed, tested, not deployed.** I found a real bug in the original customer identity key — it included `customer_name`, which meant a routine name correction would silently mint a brand new fake identity for an existing customer, breaking continuity. The fix is a durable key built from `source_customer_code` and `ship_to_customer_code` only, with `customer_name` deliberately excluded from identity and treated instead as a tracked attribute. When a name changes, the durable identity stays the same and a new version row records the change with its own effective date. I designed and tested this properly, including a migration path for the existing mapping file. It's not live in the current pipeline. dbt's `snapshot` feature is the more idiomatic place to actually implement SCD2, and I didn't want to hand build it now and then rebuild it properly in dbt later, so it's staying as a documented, tested, ready to deploy design until the warehouse layer exists.

**One quality gate script per dataset instead of one generalized script.** `data_quality_gate.py`, `data_quality_gate_open_orders.py`, and `data_quality_gate_inventory.py` are near duplicates of each other. A cleaner design would parameterize one script for all three datasets. I chose not to, because `data_quality_gate.py` was already built, tested, and working against real production data (553,098 rows) by the time the other two datasets needed the same logic. Refactoring a proven script to be generic felt riskier than a small amount of duplication. This is a real DRY violation I'm aware of, not an oversight.

**No pre existing master tables — identity had to be derived from transactions.** There's no clean list of every customer or a product catalog to join against in the source system, at least not one this pipeline has access to. `profile_customers.py` and `product_profile.py` derive the entire universe of customers and products by scanning transactional order data and building identity through hashing, rather than joining against a stable reference table. This is more fragile than a real master data join would be, and it's part of why the leading zero bug and the customer name identity bug were possible in the first place. It also means an entity only gets a pseudo identity the first time it appears in a transaction, which is exactly why the backfill stages exist. Open orders and inventory can both reference a customer or product that order history has never seen yet.

**`order_number` and `purchase_order_number` are left unmasked, deliberately.** These aren't pseudonymized like customer names or SKUs. The actual privacy risk this pipeline defends against is a stable, repeated identifier that lets someone correlate records back to a real entity over time, which is why the customer codes matter enough to hash into the identity key. `order_number` is minted once per transaction and never reused; on its own it doesn't link to anything else. Masking it would cost real analytical value (order level joins, dedup, tracking) for no corresponding privacy benefit. `purchase_order_number` is customer assigned and carries a small theoretical risk if a customer's own numbering convention happened to embed something identifying. Low severity, and accepted as a documented residual risk rather than built around.

**`company_code` and `created_by_user` were dropped, not pseudonymized.** Every row in the real data carries the same constant value. It isn't a meaningful analytical dimension, it's a fixed constant, so removing it entirely is simpler and more honest than pseudonymizing a column that never varies. `created_by_user` is a real employee username from the source system, which is personal data in its own right, separate from customer privacy entirely. The fix is to drop all three outright, since nothing downstream currently needs the raw values. They're removed inside the pseudonymization scripts themselves, not left in place and filtered out later, because the goal is to keep real identifiers from ever reaching S3 at all. Hiding them behind a later transformation while the raw values still sit in the landing zone wouldn't actually close the gap.



## Limitations

Things this pipeline genuinely does not do, stated plainly:

- **No direct database connection to the source system.** Every run depends on someone manually exporting Excel. The pipeline's freshness is bounded by that manual step, not by anything automated.
- **No pre existing master or dimension tables.** See tradeoffs above. Customer and product identity is derived from transactional scans, not joined against a stable reference table.
- **Cross dataset analysis isn't valid against what's currently on file.** The inventory snapshot I have is from February 2025; order history is from mid 2026, over a year apart. Comparing "current inventory" against "current demand" using these specific files would produce a misleading answer, so I'm not doing that analysis yet. Going forward, I'm taking all three extracts (order history, open orders, inventory) within about a minute of each other, but that's a discipline I have to remember, not something the pipeline enforces yet.
- **No scheduler.** This runs when I run it, on my machine. There's no cron job, no Airflow DAG yet, no recurring trigger. Airflow is the planned next step once the warehouse layer exists (see tradeoffs above).
- **SCD2 isn't deployed** (see tradeoffs above). The customer identity key in the live pipeline today still includes `customer_name`.
- **No incremental or CDC loading.** Every run reprocesses the full order history rather than loading only what changed. A stable `row_hash` is already computed on every row specifically so a future warehouse layer merge can use it, but nothing consumes it that way yet. This will be included later in warehouse stage. 
- **`first_half_sku_code` and `unique_sku_code`, as standalone columns in `product_mapping_final.csv`, likely have leading zeros silently stripped.** These are numeric looking codes from the source system; when a whole column looks like valid integers, pandas infers an integer type on read and drops the leading zero before anything downstream ever sees the original text. `full_sku_code` itself is unaffected, since the dash inside it forces it to be read as text, and nothing in this pipeline currently relies on the standalone columns for anything beyond internal, self consistent grouping. So this hasn't caused a functional bug so far. It would matter the moment either column is used outside this pipeline, in an external report or a join back against the real source system. Not fixed yet; the fix is a one line change forcing those columns to be read as text, the same pattern already applied in `pseudonymize_inventory.py`.
- **Inventory's SKU reconstruction assumes a fixed six digit plus five digit split.** Inventory's source SKU is a plain number with leading zeros stripped by Excel; the pipeline reconstructs `full_sku_code` by zero padding to eleven digits and inserting a dash after the sixth digit. This has matched every real SKU seen so far, and a mismatch fails loudly rather than silently producing the wrong match, but it's an assumption about how the source system encodes these codes, not a verified guarantee.
- **No automated alerting.** A failed run produces a non zero exit code and a log file. Nobody gets paged.
- **Testing is targeted smoke tests, not a coverage driven test suite.** I wrote synthetic data to specifically exercise the scenarios that mattered (a second incremental run, a customer renaming mid stream, a corrupted mapping file, two datasets sharing a folder namespace) rather than aiming for blanket code coverage. That approach caught real bugs (below) that a purely static code review didn't. The repo also includes small synthetic samples, fewer than twenty rows per dataset, so the pipeline can actually be run end to end without needing real business data.



## Debugging notes

Specific things that actually broke, and how I found them — not a hypothetical list.

**A pandas merge silently broke on the second incremental run, not the first.** `sku_mapping_pipeline.py` merges a dataframe against itself to look up prior pseudo SKU sequences. On the very first run, that code path never executes (there's nothing prior to look up yet), so it looked fine. The bug only showed up when I wrote a synthetic test that ran the script twice, first run clean, second run adds a genuinely new product, and hit a `KeyError` because pandas silently renamed a duplicate column instead of raising. Fixed by explicitly selecting only the columns needed before the merge. This is the kind of bug that a first successful run gives you false confidence about.

**A quality gate regression that would have permanently blocked every future S3 upload.** At one point, `data_quality_gate.py` started generating a fresh timestamp for its own report filename instead of reusing the batch ID already embedded in the order file's name. Nothing about that change threw an error; the gate still ran, still passed. The problem only became visible when I compared the two filenames directly and noticed they didn't match. The upload script requires those two batch IDs to match before it'll upload anything, so this would have silently failed every upload from that point on, with an error message that, without the history of what changed, would have looked like a totally unrelated bug.

**An S3 upload script that stopped checking the thing it exists to check.** A later version of `upload_pseudonymized_to_s3.py` no longer read the quality report's `overall_status` at all before uploading, meaning a failed quality gate wouldn't have stopped anything from reaching S3. It didn't error. It didn't warn. It just uploaded. I only caught this by diffing it against the working version, not by running it. This is the failure mode that worries me most in this whole project, because a script that runs cleanly and does the wrong thing doesn't announce itself.

**Migrating the customer mapping surfaced 428 duplicate identities that already existed.** When testing the fix to the customer identity key (see tradeoffs above), migrating the existing 1,770 row mapping file to the corrected schema found that those 1,770 rows only represented 1,342 actual distinct customers. The rest were name variants ("Beta Inc" / "Beta Incorporated" / "BETA INC.") that the old key design had silently issued separate fake identities for. I had to design a deterministic resolution rule (lowest numbered existing pseudo ID wins per group) and produce an audit CSV of exactly what got merged into what, rather than just picking one and moving on.

**A config file that was valid Python and also completely broken.** `column_mapping.py` got accidentally saved as literal Jupyter notebook JSON instead of a plain dict. It didn't throw a syntax error; a JSON object happens to also be valid Python dict literal syntax, so it parsed fine and then defined nothing importable. The failure showed up three files downstream as a confusing `ImportError`, not where the actual mistake was.

**One duplicate order row in 553,098.** The quality gate flagged exactly one `row_hash` collision in the largest real run so far. Traced it back to the original ingestion batch, a genuinely duplicated row already present in the source export, not something the pipeline introduced. Small enough to not block the run (it's a warning, not a failure), but it's the reason there's a documented, tested path for adding a dedup step later if this starts happening more than once in 553,098 rows.

**Two script versions silently diverged, and the wrong ones ended up live.** While building the SCD2 design as a separate set of files, the SCD2 versions of `profile_customers.py`, `customer_mapping_pipeline.py`, and `pseudonymize_order_history.py` ended up saved into the live pipeline instead of the versions that actually match the deployed `customer_mapping_final.csv` schema. The failure surfaced as a missing column `ValueError` several stages into a full pipeline run, correct behavior from the script that raised it, but confusing without knowing why two versions existed. Fixed by reverting all three files and adding a documented check (searching each file for a specific marker string) to confirm which version is actually deployed before trusting a run again.

**A glob pattern that was correct until a second dataset existed.** `upload_pseudonymized_to_s3.py` looked up its own quality report with the pattern `quality_report_*.json`. That was fine when order history was the only dataset. Once open orders started writing `quality_report_open_orders_*.json` into the same folder, the wildcard matched both, and because Python's `sorted()` treats filenames as text, and digits sort before letters, the "latest" pick landed on the open orders report instead of the genuinely newest order history one, purely by alphabetical accident. The batch ID matching check (see evaluation, below) caught it and refused to upload, so nothing shipped incorrectly, but the fix was tightening the pattern to `quality_report_[0-9]*.json`, explicitly excluding any dataset prefixed variant sharing the folder.

**A safety check that could never actually fail, and a real bug hiding underneath it.** Building inventory's SKU reconstruction, I added a check comparing the reconstructed SKU against the matched product's own stored components. That check was circular: it could only fail if the mapping file already contradicted itself, which is never true by construction, so it provided no real protection against the reconstruction logic itself being wrong. Rewriting it to check the actual precondition (every product's stored components follow a fixed six digit and five digit split) surfaced the real issue. Most real products didn't follow that pattern in their standalone component columns, not because the encoding assumption was wrong, but because those columns had already lost their leading zeros to the pandas issue noted above. `full_sku_code` itself, protected from that same issue by its dash, was always the reliable match target. The fix was removing the flawed check entirely and trusting the already correct match, while documenting the separate, real data quality issue it happened to expose.



## Evaluation

How I actually know this pipeline is doing what it claims, not just "the script exited 0":

- **The quality gate distinguishes failures from warnings on purpose.** Missing required columns, unmapped customers or SKUs, or a pseudonymization check that finds a real name leaking through — those fail the run and block the upload. A duplicate row hash or a negative quantity — those warn but don't block, because they need a human to look, not an automated rollback.
- **Batch IDs, or snapshot dates for inventory, are a structural guarantee, not a naming convention.** The pseudonymized file, its quality report, and its S3 upload path all carry the same identifier, and the upload script explicitly refuses to upload if the data file and quality report don't match. This isn't just for readability, it's what stops a stale quality report from ever getting paired with a newer, unvalidated data file. Inventory uses a day level snapshot date rather than order history and open orders' minute level batch ID, deliberately: inventory is a once per snapshot business event, not a transactional extract, and forcing minute level precision onto it would imply a timing guarantee that doesn't exist.
- **Row counts are checked across every join.** If a merge against the customer or product mapping ever produces more or fewer rows than went in, the pipeline stops instead of silently shipping duplicated or dropped rows.
- **The real evaluation method during development was adversarial smoke testing, not just running the happy path.** For every meaningful stage, I built a synthetic scenario specifically designed to break it (a second incremental run, a mid stream name change, a deliberately corrupted mapping file, two datasets sharing a folder namespace) before trusting it against real data. Several of the bugs listed above were caught exactly this way, not by code review.
- **Real production runs found bugs the synthetic tests didn't.** The script version mixup and the glob pattern collision only surfaced once three datasets existed and actually shared infrastructure (the same mapping files, the same quality reports folder). That's a category of bug that's specifically about integration between components, not any single component in isolation, and running the whole thing end to end, repeatedly, against real data, is what actually found these.
